       Post-Quantum Cryptographic Profile for BRSKI Bootstrapping
               draft-vicente-anima-brski-pqc-bootstrap-03

Abstract

   This document defines a post-quantum cryptographic (PQC) profile for
   the Bootstrapping Remote Secure Key Infrastructure (BRSKI) protocol
   (RFC 8995) and its constrained variant (cBRSKI).  The profile
   mandates ML-DSA-signed vouchers, PQC or hybrid composite pledge
   identity certificates, hybrid TLS 1.3 during bootstrap exchanges, and
   a rotation-epoch-aware Manufacturer Authorized Signing Authority
   (MASA) recording a pqc_epoch_id in every issued voucher.

   This revision (-03) expands hybrid composite certificate
   requirements, aligns with FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA),
   and adds a MASA epoch-rotation protocol conformant with draft-
   vicente-lamps-rotation-envelope.

1.  Introduction

   BRSKI [RFC8995] enables zero-touch onboarding of devices into an
   operator domain.  This document defines the BRSKI PQC Profile (BRSKI-
   PQC), constraining algorithm choices, adding a rotation-epoch voucher
   field, and specifying MASA operational requirements for epoch
   management.

   This revision aligns with FIPS 204 (ML-DSA) [FIPS204], FIPS 205 (SLH-
   DSA) [FIPS205], and draft-vicente-lamps-rotation-envelope.

2.  Terminology

   BCP 14 [RFC2119] [RFC8174] applies.

   pqc_epoch_id:
      Monotonically increasing integer identifying the MASA signing-key
      epoch.  Recorded in every BRSKI-PQC voucher.

   ML-DSA:
      Module-Lattice-Based Digital Signature Algorithm, FIPS 204.

   SLH-DSA:
      Stateless Hash-Based Digital Signature Algorithm, FIPS 205.

3.  PQC Voucher Signing

   MASAs compliant with BRSKI-PQC MUST sign vouchers using ML-DSA-65 or
   ML-DSA-87 [FIPS204].  RSA and ECDSA voucher signatures MUST NOT be
   used.  Every voucher MUST include a pqc_epoch_id field (uint32, non-
   zero) and pqc_alg_id (OID string of the signing algorithm).

4.  PQC Pledge Identity Certificates

   Pledge IDevID certificates MUST be pure ML-DSA or hybrid composite
   (ML-DSA + ECDSA P-256/P-384).  RSA and standalone ECDSA IDevIDs MUST
   NOT be provisioned in BRSKI-PQC deployments.  The PQCHC extension
   (draft-vicente-lamps-pqchc) SHOULD be included where device resources
   permit.

5.  Hybrid TLS During Bootstrap

   Bootstrap exchanges MUST use TLS 1.3 [RFC8446] with a hybrid key
   exchange: X25519MLKEM768, SecP256r1MLKEM768, or X448MLKEM1024.  Pure
   classical key exchange MUST be rejected when BRSKI-PQC is active.

6.  MASA Epoch Rotation

   MASAs MUST implement epoch-based ML-DSA signing key rotation.  Upon
   rotation, a Rotation Envelope (draft-vicente-lamps-rotation-envelope)
   MUST be published containing the prior and new epoch certificates
   with a binding signature.  Registrars MUST validate the Rotation
   Envelope before accepting vouchers under the new epoch.  Epoch
   rotation MUST occur at least every 365 days.

7.  Constrained-Device Considerations

   Class 1/2 devices MAY use SLH-DSA-SHA2-128s [FIPS205] in place of ML-
   DSA for voucher verification under explicit operator policy.  Device-
   class selection parameters are deployment-specific and not disclosed
   herein.

8.  Security Considerations

   BRSKI-PQC provides HNDL resistance via hybrid TLS, voucher forgery
   resistance via ML-DSA, and epoch replay protection via monotonic
   pqc_epoch_id.  Operators MUST maintain an epoch registry accessible
   to registrars and MUST fail closed when the registry is unavailable.

9.  IANA Considerations

   IANA is requested to register pqc-epoch-id and pqc-alg-id YANG leaf
   nodes and ML-DSA/SLH-DSA algorithm identifiers in the BRSKI voucher
   algorithm registry.
